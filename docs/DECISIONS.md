# Architecture & Technical Decisions (DECISIONS.md)

### ADR 001: 100% Client-Side Storage with Dexie IndexedDB
- **Context:** An IPTV playlist can easily contain 10,000–100,000 channels and megabytes of XMLTV EPG data.
- **Decision:** Use Dexie.js to store playlists, channels, groups, programs, favorites, and watch history in IndexedDB with compound indexes on `playlistId`, `groupId`, and `channelId`. Tiny settings remain in `localStorage`.
- **Consequence:** Zero server cost, total user privacy, offline resilience, and fast query execution.

### ADR 002: Spatial Navigation Engine Abstraction
- **Context:** Remote controls on Smart TVs require deterministic 2D directional navigation.
- **Decision:** Wrap `@noriginmedia/norigin-spatial-navigation` behind our internal `src/shared/focus` module (`useFocusable`, `FocusZone`, `FocusScope`).
- **Consequence:** UI components are decoupled from any specific navigation library and remain unit-testable and swappable.

### ADR 003: Multi-Engine Video Player Adapter
- **Context:** IPTV streams arrive as HLS (`.m3u8`), MPEG-TS streams (`.ts`), or standard MP4/WebM files. Different browsers/devices support different codecs natively.
- **Decision:** Define a `PlayerEngine` interface with three concrete adapters: `HlsPlayerEngine` (using `hls.js`), `MpegtsPlayerEngine` (using `mpegts.js`), and `NativePlayerEngine` (HTML5 `<video>`). Fallback order is automated with configurable preference.
- **Consequence:** Maximum playback compatibility across Chrome, Safari, Android TV WebView, and Tizen/webOS.

### ADR 004: CORS & Mixed-Content Strategy
- **Context:** Modern browsers enforce CORS and block mixed content (HTTP streams on HTTPS origins).
- **Decision:** Client-side detection of network fetch and playback failures with rich diagnostic modal explaining the root cause. Provide a user-configurable proxy URL template (e.g. `https://my-proxy/?url={url}`) without shipping an unmaintained third-party public proxy. Also bundle legal HTTPS test streams in the Demo mode.

### ADR 005: Client-Side Virtual Keyboard & Remote Text Entry
- **Context:** Android TV browsers sometimes fail to trigger OS soft keyboards on text inputs without user interaction.
- **Decision:** Provide a built-in 10-foot virtual keyboard with fast URL buttons (`http://`, `https://`, `.m3u8`, `.com`, `/`, etc.) alongside native input support.

### ADR 006: Synchronous Spatial Navigation Engine Initialization
- **Context:** `@noriginmedia/norigin-spatial-navigation` requires `init()` to create its `layoutAdapter` before any component calls `addFocusable`. Because child component `useEffect` hooks run before parent `useEffect` hooks, initializing inside `App.tsx` caused `this.layoutAdapter is undefined`.
- **Decision:** Call `initFocusEngine()` synchronously at module load time in `src/shared/focus/spatial.ts`, explicitly at the entry point in `src/main.tsx`, and as a synchronous pre-check in `useFocusable`.
- **Consequence:** Eliminates runtime race conditions during initial mounting and guarantees `measureLayout` always has a valid adapter.

### ADR 007: Resilient Multi-Engine Fallback, In-Player CORS Proxy Presets & Sub-Request Proxying
- **Context:** IPTV providers stream across disparate container formats (M3U8, MPEG-TS, MP4) and frequently lack CORS headers or use unencrypted `http://` streams that modern browsers block under Mixed Content security rules on HTTPS sites. In addition, when an initial engine (e.g. native HTML5 video or Hls.js) failed on unsupported formats (such as raw MPEG-TS in Chromium), the player previously retried the same failed engine repeatedly instead of progressing down the fallback chain. Furthermore, Hls.js proxies only fetched the master manifest through the proxy while sub-requests for fragments and keys still hit CORS errors.
- **Decision:**
  1. Implement deterministic multi-engine startup fallback in `PlayerManager` (trying `hls` -> `mpegts` -> `native` sequentially before declaring fatal failure).
  2. Implement sub-request proxying in `HlsPlayerEngine` using a custom `Hls.DefaultConfig.loader` extension that ensures fragment, playlist, and key URLs are routed through the configured proxy.
  3. Introduce 1-click CORS proxy presets (`corsproxy.io`, `allorigins`, `codetabs`) selectable both in Settings and directly inside the stream error overlay and diagnostic modal.
  4. Replace expired/403 test streams in the public demo playlist with verified, high-availability public feeds (Deutsche Welle HD, Apple BipBop, Mux adaptive test) and automatic IndexedDB migration.
- **Consequence:** Zero remote-typing friction for TV users encountering CORS/mixed-content errors, seamless format fallback across Chromium/Safari/TV browsers, and 100% working verified demo playback.


### ADR 008: Bug-hunt behavioural defaults
- **Context:** The bug-fix pass (see `docs/BUGS.md`) surfaced several places where the existing code was ambiguous or conflicted with the spatial-navigation library. Each needed a safe default rather than a product decision.
- **Decision:**
  1. **BACK is single-dispatch.** The global back-handler stack is driven by exactly one module-level window listener (`dispatchBack()`). Components never pop the stack themselves. This guarantees one layer per key press regardless of how many `useTvInput` instances are mounted.
  2. **Overlays own the D-pad.** When the player controls overlay or the stream-error overlay is visible, NAV_*/SELECT are yielded to the spatial-navigation engine; the player only keeps media/info/digit/color shortcuts. Auto-hide is paused while navigating.
  3. **HLS media recovery is bounded.** `HlsPlayerEngine` attempts in-place recovery twice (`recoverMediaError`, then `swapAudioCodec` + `recoverMediaError`) before reporting fatal. Network errors are never recovered locally: `PlayerManager` alone owns fallback and exponential backoff.
  4. **Async player callbacks are generation-gated.** `PlayerManager` increments a session token per load; stale `init`/error/success callbacks are dropped to protect rapid channel zapping.
  5. **Missing XMLTV `stop` defaults** to `start + 30 minutes` and timezone offsets accept both spaced and compact forms (`+0530`, `+05`).
- **Consequence:** Deterministic remote behaviour (one layer per BACK, one channel action per arrow), no player recovery races, and tolerant EPG ingestion. EPG timeline virtualization (BUG-008) is explicitly deferred: it needs a dedicated windowing + 2-D focus design and is tracked in `docs/BUGS.md`.

### ADR 009: Single lockfile policy (npm)
- **Context:** The repository currently ships two lockfiles — `package-lock.json` (npm, matches the installed `node_modules`) and a stale `bun.lock`. New guardrail tooling (Vitest, Playwright, ESLint) was installed with npm to avoid a third lockfile.
- **Decision:** npm is the single package manager. `package-lock.json` is authoritative. `bun.lock` is stale and should be removed, but is left in place for a separate, explicit cleanup.
- **Consequence:** CI uses `npm ci`. Copies of the older prompts that say `pnpm` should be read as `npm run` / `npx`. The architecture and guardrail docs are [`ARCHITECTURE.md`](./ARCHITECTURE.md) and [`GUARDRAILS.md`](./GUARDRAILS.md).

### ADR 010: Capacitor native shell with mobile/TV product flavors
- **Context:** The player must ship as an installable Android TV / Google TV / Fire TV app and a phone/tablet app, without rewriting the React client and without introducing a server. The web app already owns focus, navigation, storage and playback.
- **Decision:**
  1. **Capacitor 7 wraps the existing bundle.** One web build (`dist/`) is the single source of truth; `npx cap sync android` copies it into the Android project. No web code forks per platform.
  2. **Two Gradle product flavors, one codebase.** `mobile` (touch, portrait allowed, leanback not required) and `tv` (leanback required, touchscreen not required, landscape, `LEANBACK_LAUNCHER` entry point, `Theme.StreamwalaTv`). Per-flavor differences flow through `manifestPlaceholders` and the `src/tv/AndroidManifest.xml` overlay so `src/main/AndroidManifest.xml` stays single-source. Application ids: `tv.streamwala.iptv` (mobile) and `tv.streamwala.iptv.tv` (TV), letting both installs coexist on one device.
  3. **BACK is bridged, not duplicated.** Android delivers BACK to the Activity, so `@capacitor/app`'s `backButton` event is routed through the existing `dispatchBack()` funnel in `src/shared/input/nativeBackBridge.ts`. No second listener is registered and no raw key listener is added outside `src/shared/input` (Rule 8). When nothing consumed the press the app exits.
  4. **The shell stays thin.** `MainActivity` only sets immersive mode, keeps the screen awake, disables the media-user-gesture requirement (hls.js/mpegts.js autoplay), translates the remote OK button (`KEYCODE_DPAD_CENTER`) into `KEYCODE_ENTER` so the spatial-navigation engine's Enter activation fires on every remote, and gives the WebView focus so D-pad events reach the DOM. Playback logic remains in `src/services/player`.
  5. **Cleartext + mixed content stay allowed** via `network_security_config.xml` and `allowMixedContent`, because Xtream/M3U panels are commonly plain HTTP on private hosts.
  6. **Artwork is generated, not hand-exported** (`scripts/android-assets.py`): launcher icons, adaptive foregrounds, splash screens and the required 320×180 TV banner derive from the same brand colors as the M3 theme.
  7. **Release signing is external.** `android/keystore.properties` (gitignored) feeds `signingConfigs.release`; debug builds need no setup. WebView codec coverage is the known ceiling — a Media3/ExoPlayer engine behind the existing `PlayerEngine` interface is the follow-up if target boxes fail on TS/HEVC.
- **Consequence:** `npm run android:debug` / `android:release` produce four APKs (`streamwala-{mobile,tv}-{debug,release}.apk`) from one web build. Full instructions, verification commands and the device test matrix live in [`ANDROID.md`](./ANDROID.md).

### ADR 011: Soft keyboard (IME) on touch devices is a shell concern
- **Context:** BUG-018 — the mobile APK showed no soft keyboard for any text input. `MainActivity` set `webView.setFocusableInTouchMode(false)` unconditionally. That is required on TV (no touch; D-pad must own focus) but on a touch device it prevents the WebView from taking focus from a tap, so the WebView is never bound to the input method and Android raises no keyboard.
- **Decision:**
  1. The touch-vs-TV decision is **data, not code**: each flavor declares `resValue "bool", "streamwala_touch_device"` (`mobile` → `true`, `tv` → `false`) and `MainActivity` reads it for `setFocusableInTouchMode`.
  2. The IME must be able to resize the page: the single activity declares `android:windowSoftInputMode="adjustResize"`.
  3. The global `user-select: none` from the 10-foot shell is overridden for `input`, `textarea` and `[contenteditable='true']`, because some WebViews will not place a caret in an element that cannot select text.
  4. The behaviour is locked with an instrumented test (`MainActivityImeTest`) that launches the activity and asserts both the touch-mode focus value for the running flavor and the resize soft-input mode, since jsdom cannot observe native focus or the IME.
- **Consequence:** Phones/tablets raise the OS keyboard on tap while the TV build keeps touch-mode focus off. Any future flavor (e.g. a tablet-only build) only needs the boolean resource; no branching in `MainActivity`. The in-app virtual keyboard remains the TV path and a fallback everywhere.

### ADR 012: Theme variants must redefine every M3 token
- **Context:** BUG-019 — Settings offered Dark / AMOLED / Light, but Light rendered identically to Dark. `applyTheme()` correctly added `theme-light` to `<html>`, yet `src/index.css` only defined token blocks for `:root` (dark) and `html.theme-amoled`; with no `html.theme-light` block the dark values stayed in force.
- **Decision:**
  1. The class toggled by `applyTheme()` (`theme-light`, `theme-amoled`) is the single switch for a palette; CSS owns the values and components never branch on theme.
  2. A variant that changes surface tone must restate **every** `--md-sys-color-*` token the `:root` dark block declares, plus `color-scheme` so native controls and scrollbars follow. Partial overrides are allowed only for deliberate near-duplicates (AMOLED restates surfaces only, by design).
  3. Non-video surfaces use tokens (`surface-container-highest`, `outline-variant`, focus-ring token) rather than `bg-black/*` or `bg-white/*` alpha literals. Black-alpha remains acceptable only for scrims over the video plane.
  4. The parity rule is locked by `src/app/settingsStore.test.ts` (parses `src/index.css`, asserts the light block covers every dark token) and a Playwright assertion that the light body background is bright and distinct from dark.
- **Consequence:** Adding a theme variant without a full palette fails `npm test` instead of silently shipping a look-alike. Future variants must also be added to the `cases` table in that test.

### ADR 013: Navigation — permanent icon-only rail; labels via aria only; hints moved to content footer
- **Context:** The previous side drawer was `position: fixed` over the content, clipped hero text at the left edge, expanded on hover/focus into a ~256 px labelled panel (wasting ~230 px of a 10-foot screen) and crammed the wordmark plus a colour-key legend into the sidebar. It also relied on the library's inverse boolean polarity for arrow presses (BUG-001 class) and had no active-vs-focused distinction at 3 m.
- **Decision:**
  1. Replace the drawer with a permanent `NavigationRail` that lives **in normal layout flow** (`rail | content` flex row, never `position: fixed`), is exactly `--rail-width` wide and never expands. Content starts at the rail's trailing edge plus the standard safe-area padding, so the drawer's `ml-20` hack is gone.
  2. Icon-only: logo mark (no wordmark/subtitle), Home / Live TV / EPG Guide / Favorites / Search vertically centred, Settings pinned to the bottom. Icons are `<Icon/>` Material Symbols Rounded at `--rail-icon-size`; every item is a `--rail-item-size` square hit target whose accessible name comes from `aria-label` only. Active = `secondary-container` pill + filled icon + `aria-current="page"`; focused = 3 px `--md-sys-color-primary` ring + scale 1.06. Motion is limited to `transform`/`opacity` and honours `prefers-reduced-motion`.
  3. Focus rules live in the `NAV_RAIL` zone and use only `shared/focus` wrappers: LEFT enters on the active item (`preferredChildFocusKey`, `saveLastFocusedChild: false`); UP/DOWN stop at the ends (focus boundary for `left`/`up`/`down` plus `BLOCK_NAVIGATION` sentinels with a one-line reason each); RIGHT restores the last content element remembered by `src/shared/focus/contentFocusMemory.ts`; OK navigates on `onEnterPress` only and lands focus on the new screen's primary target; BACK closes overlays first, then focuses the rail.
  4. `FocusScope` was added to `shared/focus` because `useFocusable` reads its parent from `FocusContext` and the library does **not** provide that context automatically — without it a container's `preferredChildFocusKey`/focus memory is silently ignored (children register against the ROOT).
  5. The colour-key legend moved out of the rail into a slim `RemoteHintBar` at the bottom of the content area, gated by a new persisted `showRemoteHints` setting (default on) and naturally hidden on the player route. The shortcuts themselves are unchanged.
  6. The rail is not rendered on the player, onboarding or other fullscreen routes; pointer clicks still navigate and follow the existing `:focus-visible` behaviour.
- **Consequence:** No content is clipped or overlapped at 1280×720, 1920×1080 or 3840×2160 (asserted in `e2e/navigation-rail.spec.ts`); active and focused states are distinguishable at 3 m; the whole app is D-pad navigable and BACK ordering is preserved. Geometry is documented in [`DESIGN_TOKENS.md`](./DESIGN_TOKENS.md) and focus rules in [`TV_INPUT.md`](./TV_INPUT.md).

### ADR 014: Focus zones own their children; a D-pad stop is always a control
- **Context:** BUG-020 — the Settings screen was dead to the remote. `FocusZone` rendered a focusable `div` but never provided `FocusContext`, so its children registered against the ROOT. The library navigates strictly between *siblings* and only descends into a component's children when focus is set on that component, so a zone with root-level children was a stop of its own: focus landed on the container, which has no `tv-focus-target`/`tv-focused` styling, and every subsequent arrow press appeared to do nothing. The settings tiles compounded it by being raw `<button>` elements that never called `useFocusable`, and `Card isInteractive={false}` was still a focus stop. `e2e/dpad.spec.ts` could not see any of this because it only asserted `document.activeElement`, which a mouse click leaves on the rail.
- **Decision:**
  1. **`FocusZone` owns its children by default** (`ownsChildren` → `FocusScope` from `shared/focus`). This is the pattern ADR 013 (4) already prescribed for the rail; it is now the default for every zone. Because a zone with focusable children is only ever a *routing* node — `setFocus`/`smartNavigate` descend to the last-focused or nearest child — a zone is never the final focus target unless it has no focusable children at all.
  2. **`focusZone` is not a stop by accident.** `FocusZone` accepts `focusable={false}` for pure layout wrappers, and `Card` passes `focusable: isInteractive` so a non-interactive card can never be focused.
  3. **Anything the remote can reach must be a real control.** Styled non-button tiles are wrapped in the local `FocusableTile` (settings) or the matching `shared/ui` primitive, so every stop carries `tv-focus-target` + `tv-focused` and an `onEnterPress` handler. The settings tab row is a zone (entry target is the active tab tile, `SETTINGS_TAB_*`), and each card section is a zone with explicit `SETTINGS_SECTION_*` keys.
  4. **The guardrail asserts the property, not the mechanism.** `e2e/dpad.spec.ts` now requires that after every arrow press on every top-level screen the engine's `[data-focused="true"]` element exists and has `tv-focus-target` (and it polls first, because async screens such as the EPG settle their focus a moment later). `e2e/settings-dpad.spec.ts` walks the settings screen and asserts the same, plus OK activation.
- **Consequence:** Focus on every screen lands on a visible, activatable control, and flat root-level sibling sets no longer cause the geometry heuristics to jump between unrelated sections (DOWN in settings now walks section by section). New zones get the tree behaviour for free; a zone that intentionally stays flat must opt out and say why. Any future non-`tv-focus-target` focus stop fails `npm run e2e`.

### ADR 015: Focus-driven scrolling via a transform axis
- **Context:** Scroll position was a side effect of `useFocusable` calling `el.scrollIntoView({ behavior: 'smooth', block: 'nearest', inline: 'center' })` on every focus change. `block: 'nearest'` pinned focused cards to the screen edge, `behavior: 'smooth'` stacked animations on held keys, the Home hero was clipped mid-state, headings were cut off at the top, and a parent `overflow-x-auto` clipped the 3 px focus ring / `scale(1.04)` at the left edge. Longer screens (100k-channel lists, the EPG) were unvirtualized.
- **Decision:**
  1. **Scrolling is derived from focus and owned by `src/shared/scroll`.** The focus hook no longer scrolls. Scroller hooks observe the engine's `data-focused="true"` marker and compute an offset from the item's `data-scroll-index`/`row`/`col`/`x` (index math), then animate the content with a **transform** (`translate3d`) on a retargetable rAF tween. A new target retargets the in-flight tween; there is no queue, no `scroll-behavior: smooth`, and no `scrollTop` animation.
  2. **Focus line = 0.38.** Row-snap screens anchor the focused row's top at 38% of the viewport so the next row peeks; `focusLine` is a config token. Offsets clamp to `[0, content − viewport]`, so the first rows rest at the top and the last rows rest at the bottom.
  3. **Hero has two discrete states.** Expanded/collapsed are toggled with classes on a **single, non-remounting DOM tree** (branching the JSX dropped DOM focus to `<body>`), with only `opacity`/`transform` transitions. The row-snap re-anchors the focused row when hero metrics change.
  4. **Grids/lists use minimal scroll + index-math windowing.** Columns are derived from viewport width; `VirtualGrid` keeps the full content height for clamping and renders only visible rows plus overscan, so 100k items stay responsive. Held keys are throttled/accelerated in `src/shared/input`, and `PageUp`/`PageDown`/`CH±`/digits jump by rows.
  5. **The 3 px ring is never clipped.** Scroll content reserves `--focus-ring-pad`; a Playwright spec asserts the ring bounds stay inside the nearest clipping container at 720p/1080p/4K.
  6. **Scroll + focus memory** is module-level (survives the player/dialog/route unmount) and restored offset-first so the window renders the row before focus is set.
- **Consequence:** The focused item is always fully visible and ring-intact, row-snap screens rest on the focus line, held-key scrolling settles cleanly with no stacked tweens, restore is exact, and `streamwala/no-adhoc-scroll` plus `e2e/scroll.spec.ts` prevent regressions. Model and config are documented in [`SCROLLING.md`](./SCROLLING.md).

### ADR 016: Secrets and local files are ignored by category, not by accident
- **Context:** `.gitignore` had accreted ad-hoc entries (`node_modules/`, `dist/`, `coverage/`, `.env*`, `.DS_Store`) with duplicated test-artifact blocks and no coverage for editor noise, keys, cloud credentials, or IPTV data. Xtream Codes playlist URLs embed the username and password in the URL (`http://host/get.php?username=USER&password=PASS`), so a single `.m3u` dropped in the working tree is a credential leak — and `*.m3u8` is also the HLS playlist extension, so both must be ignored while sanitized fixtures stay committed.
- **Decision:** `.gitignore` is organised into commented sections — dependencies, build/tooling output (including Capacitor/Android native output and PWA/Workbox artefacts), tests and coverage, logs, editor/OS noise, secrets, IPTV data, local agent scratch files, and a final negation block. Secrets are ignored broadly: `.env` and every `.env.*` except `.env.example`; private keys and certificates (`*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa*`, `id_ed25519*`); cloud/service credentials (`*credentials*.json`, `service-account*.json`, `.npmrc`, `.netrc`, `.aws/`, `.gcloud/`, `.firebase/`, `.vercel/`, `.netlify/`); and IPTV payloads (`*.m3u`, `*.m3u8`, `*.xmltv`, `*.epg.xml*`, `playlists/`, `xtream/`, `local/`, `private/`, settings/backup exports). Negations only re-include items the repository intends to keep: `.env.example`, both lockfiles, `src/test/fixtures/**`, a future `public/sw.js`, `AGENTS.md`, `README.md` and `docs/**`.
- **Consequence:** Untracked leaks are caught before `git add`, sanitized fixtures remain committable, and no currently tracked file matches an ignore rule (verified with `git check-ignore -v` over `git ls-files`). `.gitignore` is not a history cleaner: it does not affect already-tracked files, so a committed secret still needs rotation, `git rm --cached` and history rewriting (see `AGENTS.md` §5). Android keystore material (`android/keystore.properties`, `*.jks`) is ignored at both the root and the Capacitor shell level.

### ADR 017: Virtualized item sizes are measured, not hard-coded in px
- **Context:** BUG-022 — `ChannelGridCard`, `ChannelListItem`, `FavoriteCard` and `SearchChannelCard` were handed a fixed px height (`208`/`168`) that had to equal the scroller's `rowSize` for index math to hold, but every inner size (Tailwind spacing/typography) was authored in rem. `1rem` follows the viewer's font size (browser/Android TV font scaling), so above the default 16 px the content became taller than the box; because the card is a flex column, flex shrank the `h4`/`p` line boxes and `overflow-hidden` cropped the channel name and group. Even at 16 px the grid card was 2 px short. Raising the constant is not a fix: any px height is wrong for some font size, and making it rem-proportional is also wrong at small sizes (the icon's px floor dominates there).
- **Decision:**
  1. **Cards are content-sized with a rem floor.** They declare a rem `min-height` (uniform rows, no collapse when a field is absent) and never set a px height, so the rendered row is exactly as tall as the typography demands.
  2. **The scroller measures the real cell.** `useGridScroller` gained `measureItemHeight?: boolean`; when on, `useMeasuredItemHeight` reads the first rendered cell's `offsetHeight` on a layout pass (`ResizeObserver`, mount/resize only — never on the focus hot path, per [ADR 015](#adr-015-focus-driven-scrolling-via-a-transform-axis)) and `useGridScroller` returns the measured `itemHeight`/`rowSize` for `VirtualGrid`, `ScrollPositionIndicator` and row-jump math. The `rowSize` option is now only the first-paint fallback.
  3. **Measurement uses `offsetHeight`, not `getBoundingClientRect`.** The focused card's `scale(1.04)` transform must never feed back into the row pitch.
- **Consequence:** Channel names and group labels survive any root font size or browser zoom, the grid/list/row pitch always equals the real layout (no window/offset desync), and new virtualized grids follow the same pattern: rem `min-height` on the cell + `measureItemHeight: true`. Documented in [`SCROLLING.md`](./SCROLLING.md); regression coverage in `e2e/channel-cards.spec.ts`.

### ADR 018: EPG is a per-playlist, multi-source, streaming pipeline behind a repository
- **Context:** A playlist can carry thousands of channels and a 100 MB XMLTV file, EPG hosts routinely block CORS, Xtream URLs embed credentials, and the previous code had a dead `DOMParser` parser and an un-virtualized 30-channel guide stub. The guide must be accurate across time zones and never wipe existing data on a failed refresh.
- **Decision:**
  1. **Pure domain core.** `src/domain/epg` owns XMLTV time parsing (`time.ts`), channel↔XMLTV matching (`matching.ts`) and Now/Next (`nowNext.ts`). No React, no I/O, fully unit-tested.
  2. **Streaming ingestion.** `fetcher` streams the response (byte progress, `AbortController`, timeout), sniffs gzip by magic bytes (`1f 8b`) with `Content-Encoding`/extension only as a short-head fallback (so an already-decoded body is never double-decompressed), and classifies CORS/mixed-content/timeout into credential-safe errors. Parsing runs in a **lazy-loaded worker** with a hand-written tolerant SAX-style tokenizer (no `DOMParser`, no new dependency). Programmes outside the retention window (−1 d/+3 d) or for unmatched channels are discarded while streaming.
  3. **Multi-source, per playlist.** `epgSources` are merged by priority; a channel has one resolved `epgMapping` (`manual` always wins). Matching is tiered (exact `tvg-id` → normalized name with quality-tag stripping → conservative fuzzy with a required margin); ties are never auto-mapped.
  4. **Repository boundary.** All persistence is behind `EpgRepository` (Dexie implementation + in-memory fake). Per-channel programme writes are an atomic swap, pruning only deletes `stop < now`, and playlist/source deletes cascade. Screens never hold the full EPG in React state — they query channel + window.
  5. **Runtime owns scheduling.** `app/epgRuntime` drives a scheduler with one refresh per source, dedupe, capped exponential backoff, TTL stale-while-revalidate, offline pause/resume and a single `getNowNext(channelId, now)` selector.
  6. **Guide virtualization.** The timeline virtualizes rows (measured rem height) and the channel column, scrolls horizontally via `shared/scroll`, and pins the header/column. The Guide and the settings EPG panel are lazy chunks so the initial bundle is not burdened.
  7. **Credentials stay secret.** Xtream XMLTV URLs are masked in the UI and never reach logs, error text or caches; sanitized fixtures live in `src/test/fixtures/epg/`.
- **Consequence:** An existing playlist gains a guide by URL, header auto-detect, Xtream derivation or local file using only the D-pad; large files do not freeze the UI; a failed refresh keeps the old guide; and Now/Next plus the Guide are time-zone correct. Documented in [`EPG.md`](./EPG.md); coverage in the `domain/epg`, `services/epg` and guide/settings suites plus `e2e/epg-guide.spec.ts`.

### ADR 019: Renamed to Streamwala; storage keys unchanged for backward compatibility
- **Context:** The app, formerly “Aether IPTV” (also seen as “StreamDeck TV” in older prompts), was renamed to **Streamwala**. A rename must not orphan data that already lives on users' devices. Three classes of identifier embed the old brand string:
  1. **IndexedDB** — the Dexie database name `AetherIptvDatabase` (playlists, channels, groups, programs, history, EPG sources/mappings).
  2. **localStorage** — the settings key `aether_iptv_settings_v1`.
  3. **Android identity** — the `applicationId`/namespace `tv.aether.iptv` (+ `tv.aether.iptv.tv`), the Java package `tv.aether.iptv`, and the release keystore file/alias `aether-release.jks` / `aether`. Changing the application id or keystore would create a *new* app/data identity: a second installed app with empty data, a failed in-place update, or an unshippable signed release.
- **Decision:**
  1. **Display name only.** User-facing brand strings use the `PRODUCT_NAME` constant in `src/shared/product.ts` (HTML `<title>`, onboarding, About, manifest/metadata). Package/slug is `streamwala`; internal prefixes are `STREAMWALA_` / `streamwala_` (env `STREAMWALA_JAVA_HOME`, resource `streamwala_touch_device`, colors `streamwala_*`, CSS `--streamwala-color-key-*`, ESLint plugin `streamwala/*`, `Theme.StreamwalaTv`, APK `streamwala-*.apk`). The “Leanback Edition” subtitle is dropped.
  2. **Persisted on-device data identifiers are frozen.** `AetherIptvDatabase` and `aether_iptv_settings_v1` stay exactly as shipped. Both are annotated in-source and in this ADR. If a future change is truly warranted it must be a **versioned migration** (Dexie `.version(n).upgrade()` + reopen-preservation test; a read-old/write-new localStorage shim) — never a silent rename.
  3. **Keystore alias and filename unchanged** (owner decision). `aether-release.jks` / `keyAlias=aether` stay as-is: the alias is bound to the existing signing key material, and changing it would require importing/generating a new key and would break the app's signing identity and update path.
  4. **Android application id and Java package renamed** (owner confirmed the app has **never been distributed** — no Play listing and no installed base to update in place). `applicationId`/namespace moved `tv.aether.iptv` → `tv.streamwala.iptv` (mobile flavor) and `tv.aether.iptv.tv` → `tv.streamwala.iptv.tv` (TV flavor); the Java package moved `tv.aether.iptv` → `tv.streamwala.iptv` with sources relocated to `android/app/src/{main,androidTest}/java/tv/streamwala/iptv/`; `capacitor.config.ts` `appId` and `strings.xml` `package_name` / `custom_url_scheme` were updated to match. Had the app ever shipped, this would instead be a Play Store `applicationId` migration (new listing/identity), not a rename.
  5. **No PWA/service-worker rename surface exists yet.** The repo has no web app manifest, no service worker and no Workbox config; when one is added it must reuse the same origin/scope so Cache Storage is not orphaned.
  6. **TV banner updated to a letter “S” tile.** `scripts/android-assets.py` previously drew the old “Aether”/“IPTV” wordmark onto `drawable-nodpi/tv_banner.png`. It now draws a centred letter **“S”** tile using the existing M3 tokens (`ACCENT_DIM` plate, `ACCENT` glyph) and no wordmark, matching the mark-only launcher icons/splashes and the icon-only navigation rail. The banner was regenerated in this change.
- **Consequence:** The tab title, install prompt, About screen and Android label all read “Streamwala”, while every existing user keeps their saved playlists, favourites, settings and EPG. `e2e/dpad.spec.ts` and `e2e/settings-dpad.spec.ts` still assert against the legacy storage key on purpose, and `e2e/epg-guide.spec.ts` against the legacy database name, so a future accidental rename of either fails the suite.

### ADR 020: GPL-3.0-only, DCO plus a relicensing grant, trademark reserved
- **Context:** The project is heading for its first public push. It needs a license, a way to accept contributions, and a decision about the name. A plain DCO only certifies provenance; it does not let the owner relicense a contribution later. That matters if Streamwala is ever dual-licensed or offered under a commercial license, because the owner would otherwise need permission from every past contributor for every line they touched.
- **Decision:**
  1. **License.** The code is GPL-3.0-only. The unmodified text from gnu.org is in `LICENSE`, and `package.json` sets `"license": "GPL-3.0-only"`. Per-file headers are deliberately not required.
  2. **Contributions.** Every commit needs a `Signed-off-by:` line. That certifies the Developer Certificate of Origin 1.1 (text in `DCO`) and also grants the project owner a perpetual, worldwide, irrevocable license to use, modify and sublicense the contribution, including under other license terms. The grant is what makes relicensing possible; the DCO alone is not enough.
  3. **Enforcement.** `.github/workflows/dco.yml` fails a pull request whose commits lack a valid sign-off. `CONTRIBUTING.md` documents `git commit -s`, `git commit --amend -s` and `git rebase --signoff`. `AGENTS.md` requires agent-made commits to be signed off too.
  4. **Trademark reserved.** The Streamwala name and logo are not covered by the code license (see `NOTICE`). Forks are welcome, but they must not be presented as the official build.
  5. **How to dual-license later.** The grant in point 2 means the owner can publish the same code under another license without contacting contributors. The mechanics are to pick the second license, add it as an option in the README and `package.json`, and keep accepting contributions under the same grant. A signed CLA through a service such as CLA Assistant would be stronger than DCO plus a grant if contribution volume or a real commercial deal justifies the extra process; it can be layered on top of the existing DCO check later.
- **Consequence:** The project is GPL-3.0-only with a clear contribution path, the owner keeps the option to relicense, and the name stays protected. Anyone who wants to use the code commercially has to honor the GPL or obtain a separate license from the owner.

### ADR 021: One generated brand mark — geometric "S" plate plus a tertiary live pip
- **Context:** The artwork had drifted into two marks. Launcher icons, adaptive foregrounds, round icons and splash screens drew a filled play triangle on a rounded plate, while the TV banner drew a *typeset* letter "S" using whichever bold TTF happened to be installed (`FONT_CANDIDATES` / `load_font`). That broke the "banner = icon = rail" consistency the mark-only launcher work was aiming for (ADR 019 item 6), made the banner's rendering machine-dependent — which contradicts the point of generating the artwork at all (ADR 018) — and left the brand with no element that is not a plain primary tone.
- **Decision:**
  1. **One mark everywhere.** `draw_mark()` produces the plate, the glyph and the pip as a single unit; launcher icons, adaptive foregrounds, legacy square/round icons, every splash density and the TV banner all call it. There is no second drawing path.
  2. **The "S" is drawn geometrically, never typeset.** Two 270-degree elliptical bowls that meet tangentially at the centre: the upper bowl opens right, the lower bowl opens left, and both are horizontal where they join. `FONT_CANDIDATES` and `load_font` are deleted, so the assets no longer depend on an installed font. Constructions that were tried and rejected because they do not read as an S: half-ellipse bowls joined by a straight segment (reads as "Z"), a single-oscillation cosine spine (reads as a slash), and a 1.5-oscillation cosine spine (reads as a lightning bolt, because the bowl reversals are instantaneous instead of broad).
  3. **Palette is existing tokens only.** Plate `#1B4578` (`--md-sys-color-primary-container`), glyph `#A0CAFF` (`--md-sys-color-primary`), pip `#D6BDFB` (`--md-sys-color-tertiary`). No new colour enters the brand. Measured contrast: glyph-on-plate 5.71:1, pip-on-plate 5.78:1.
  4. **A negative-space play aperture was rejected on measurement, not taste.** Punching the triangle out of the plate resolves to `#0B0C13` behind it, which is 2.02:1 against the plate — it disappears at the 24px navigation-rail size. A filled glyph is 5.71:1. The pip is also kept from touching the glyph, because tertiary-on-primary is 1.01:1 and any overlap would be invisible.
  5. **Geometry lives in one constants block, as fractions of the plate side** (`PLATE_RADIUS`, `GLYPH_RX`, `GLYPH_RY`, `GLYPH_STROKE`, `PIP_RADIUS`, `PIP_CENTRE`). The pip is kept fully inside the plate, never straddling the rounded corner, so an adaptive-icon mask cannot clip it, and is held at least 9% of the plate side away from the glyph — 4.8px at the smallest rendered size. The first geometry tried left 3.6% (1.7px) and the pip read as part of the glyph.
  6. **Thick-line joints are stamped with discs.** PIL's `joint="curve"` leaves 1px pinholes where chords meet on a convex curve and provides no round line caps; the stroke is therefore the union of the polyline and a disc at every vertex.
- **Consequence:** Banner, launcher icon, splash and rail mark are one shape, and `npm run android:assets` produces byte-identical artwork on any machine with Pillow installed — no font dependency. ADR 019 item 6 is superseded in *mechanism* (the banner no longer typesets an "S") but not in intent: the banner is still an "S" tile, still mark-only, still without a wordmark.

### ADR 022: Brand splash owns the cold boot — static paint, then React, then a first-boot-only gate
- **Context:** A cold start presented three unrelated screens. The native shell showed the mark for as long as the WebView took to launch (`AppTheme.NoActionBarLaunch` with `android:background="@drawable/splash"`, dismissed on the Activity's first draw). The WebView then painted an empty `#0b0c13` page for the whole bundle download/parse — unbounded on TV hardware — because `src/main.tsx` renders synchronously with nothing to show. And once React had mounted, `refreshData` opened IndexedDB, ran the `.version(1)→.version(2)` Dexie migration and read playlists/channels *after* first paint, so the Home shell was briefly visible with a suppressed hero and a "Live Streams" row of zero items. Three different-looking screens, two of them blank, for one boot.
- **Decision:**
  1. **The pre-React gap gets real pixels, not a colour.** `index.html` carries a `.boot-splash` inside `<div id="root">`, styled by an inline `<style>` because the bundled stylesheet is loaded by the module script and therefore does not exist yet. React's first commit replaces it — `createRoot()` clears the container's pre-existing children — so there is no coordination code, no second node and no flash. That the static mark *is* replaced is load-bearing, so it is covered by a regression test rather than assumed.
  2. **React takes over the same pixels.** `AppSplash` renders the same mark at the same size in the same place and only then adds the wordmark and tagline, which the static layer deliberately omits (it has no access to the webfonts and must not depend on them).
  3. **The gate is first boot only.** The boot sequence (`src/app/useAppBoot.ts`) owns the playlists → active playlist → channels + groups read. Nothing waits on EPG: the guide refreshes in the background behind its own progress UI. `EpgProvider` moves behind the gate so no scheduler pass runs against a screen that cannot be interacted with. Later reloads — EPG change, Settings "refresh", onboarding completion — keep the previous data and the previous inline behaviour: a full-screen splash mid-session would be a regression, so the first-boot flag is commented as intentional.
  4. **Timing is a floor plus a cross-fade.** The splash is held for at least 400 ms measured from its first paint and then cross-faded over 180 ms with the app already mounted underneath, so a warm boot does not strobe and a cold boot never shows a half-painted shell. `prefers-reduced-motion: reduce` skips the pulse and the fade (instant swap) but not the floor. A hard 8 s cap releases the splash if the storage layer never settles; the existing failure path already falls through to onboarding or the empty shell, so no error screen is invented for a case with no evidence behind it.
  5. **Input is ignored while the splash is up.** The colour keys mutated `activeNavId` regardless of boot state, so a user pressing their remote at a splash could land in Settings or the Guide the instant it cleared. A 10-foot splash is not a place to buffer input.
  6. **One mark, three consumers.** `scripts/android-assets.py` gains a `write_web_brand()` that emits `src/shared/ui/brand/streamwala-mark.svg` and `public/favicon.svg` from the same constants block as the Android rasters, and rewrites the inline copy between `<!-- streamwala-mark:start -->` and `<!-- streamwala-mark:end -->` in `index.html`. The SVG uses a `viewBox` of `0 0 1000 1000` so every fraction constant carries over unchanged, and `stroke-linecap/linejoin="round"` reproduces the disc stamping that PIL needed for round joins (ADR 021 item 6). No hand-pasted copy of the mark exists anywhere, so the drift that produced ADR 021 cannot recur.
  7. **Raw hex in `index.html` is a sanctioned exception to "never hardcode colours".** The pre-React shell cannot read CSS custom properties defined by a stylesheet that has not loaded. The three surface values it needs (default, light, amoled) and the mark size are therefore literals — and are asserted against `src/index.css` and the generated SVG by a test, because an untested exception is how the dark/light first-frame mismatch survived this long.
  8. **The theme is applied before first paint.** `index.html` runs a small inline pre-script that reads the frozen legacy key `aether_iptv_settings_v1` and adds `theme-light` / `theme-amoled`, and `settingsStore` applies the full theme at module load instead of only from an effect inside `App`. Light and amoled users previously got a dark first frame; the static splash would have made that a dark splash followed by a light app.
  9. **Collateral fixes in the same blast radius.** `theme-color` was `#0d0e15` while every other surface token said `#0b0c13`; `LinearProgress`'s indeterminate bar animated against a `@keyframes indeterminate` that existed nowhere, so it sat still; and the repo shipped no favicon at all. All three are fixed here, and the favicon comes out of the generator.
- **Consequence:** A cold boot reads as one continuous surface: native splash → static mark → React splash with the wordmark → cross-fade into the loaded app, in the user's own theme. The mark is still generated once and never hand-exported, and `scripts/android-assets.py` now writes web assets too, so `npm run android:assets` must be run (and its `src/` + `index.html` output committed) whenever brand geometry changes — CI has no Python, so `src/shared/ui/brand/brandAssets.test.ts` is the guard that the committed SVG, the favicon, the inline HTML copy and the Python constants still agree. Not covered by jsdom or Playwright: the native-splash-to-static-splash handoff, which is only observable on a device. The web mark is sized at `35vmin`, i.e. 0.35 of the shorter viewport side — the bottom of the native splash's 0.35–0.54 range, matching the densest TV bucket (`drawable-land-xxxhdpi`, 0.352) so the mark does not resize as the native splash goes away.

### ADR 023: The CORS proxy is a fallback transport, never the default path
- **Context:** BUG-023. `PlayerManager` rewrote *every* stream URL through `settings.proxyUrlTemplate` and had no direct path, so selecting a CORS proxy made the whole playlist depend on that proxy being alive. Public proxies are not reliable infrastructure: while investigating, `api.allorigins.win` and `api.codetabs.com` both returned **522** and `corsproxy.io` returned **403** (`This domain has been blocked and can't be proxied`) for `playout.now3.amagi.tv`, while that origin answered `200` with `access-control-allow-origin: *` for the manifest *and* its segments. One tap on the error overlay's "Try with CORS Proxy" therefore persisted a setting that broke playback for every channel — including the ones that never needed a proxy.
- **Decision:**
  1. **Transport planning is a pure domain concern.** `src/domain/transport.ts` owns `planTransports()`, `applyProxyTemplate()` and `isProxiableUrl()`. It receives the page protocol as an argument instead of reading `window`, so the policy is unit-testable without a browser and stays out of the service layer.
  2. **Direct first, proxy second.** The plan for a normal `https://` stream with a proxy configured is `['direct', 'proxied']`: the origin is attempted with every engine, and only a real failure (CORS/network/decode) moves playback to the proxy. A dead proxy can no longer break a working stream, and the proxy is still reached automatically when it is actually needed.
  3. **Mixed content inverts the order.** An `http://` stream on an `https://` page is blocked by the browser before a request is made, so the plan is `['proxied']` — direct is not a transport there, it is a guaranteed failure.
  4. **Engine × transport, not engine-or-transport.** `PlayerManager` keeps its deterministic engine fallback (`hls` → `mpegts` → `native`) *inside* each transport, then moves to the next transport with a fresh engine run. Terminal failure therefore requires every engine on every planned transport to fail, and the reported `engineIndex`/`totalEngines` now count that full matrix. Mid-stream failures keep the bounded exponential-backoff reconnect on the current transport before the other transport is considered.
  5. **The working transport is remembered per host, in memory only.** `PlayerManager.transportMemory` maps `host → transport` for the session so zapping between channels of one provider does not repeat a known-failed attempt. It is deliberately not persisted: surviving a reload is exactly the bug.
  6. **A template without `{url}` is not a template.** `applyProxyTemplate` returns `null` and the plan falls back to `['direct']`, because `template.replace('{url}', …)` on a token-less template silently replaces the stream URL with the proxy root. That is the same "every channel broken" class of failure, one keystroke away.
  7. **An explicit opt-in still goes proxy-first.** The error overlay's "Try with CORS Proxy" (`retryWithProxy`) starts at the proxied transport — the user just watched direct playback fail — while keeping the remaining transports as the fallback.
  8. **Subscription remains an honest dependency.** Sub-request proxying (fragments, keys, playlists) in `HlsPlayerEngine` is enabled only when the attempt is on the `proxied` transport, so a direct attempt never has its segments rewritten through a proxy that the plan did not choose.
- **Consequence:** A configured proxy can no longer break playback that works without it, and the public proxy presets in Settings became safe to try. The cost is one failed direct attempt before the proxy on the first load of a channel whose host genuinely needs a proxy; the shared per-host memory (`src/services/net/transportMemory.ts`) removes it for the rest of the session. `PlayerManagerState.transport` exposes the last transport tried so the error overlay can say that the configured proxy was reached and also failed.
- **Follow-up (done in BUG-024):** the policy is no longer player-only. `src/services/net/transportFetch.ts` applies the same plan to every non-player fetch — EPG download and detection, the Xtream client and the onboarding M3U import — and records the working transport in the shared memory, so one discovery benefits every surface. A transport is abandoned on a rejected request or a transport-level status (401/403/407/429/5xx); 404/410 are content answers and are returned as-is. `timeoutMs` gives each attempt its own budget, so a black-holed direct attempt cannot starve the proxy attempt. `buildProxiedUrl` in the EPG fetcher was deleted: `applyProxyTemplate` is the only place a proxied URL is built.

### ADR 024: The git tag is the release — one workflow builds the web bundle and both signed Android artifacts
- **Context:** Until now a release was a manual ritual: build the web bundle, remember to run `cap sync`, hope `android/keystore.properties` was present, assemble two APKs, and hand-attach them to a GitHub Release. Every one of those steps can silently degrade. `android/app/build.gradle` deliberately *skips* `signingConfigs.release` when the keystore file is absent, so a clean checkout produces a release APK that is unsigned — a build that succeeds and an artifact that cannot be installed. The version was hard-coded (`versionCode 1`, `versionName "1.0"`), so two releases were indistinguishable to Android and the second would never update the first. And the two form factors were buildable but the *packaging* (`.aab`) had no path at all, which a Play upload needs.
- **Decision:**
  1. **The tag is the only trigger and the only source of the version.** `.github/workflows/release.yml` fires on `push` of `v*`, and `versionName`/`versionCode` are derived there (`major*1000000 + minor*1000 + patch`) and injected as Gradle properties. Nothing in the repository records a version, so a version can never disagree with the tag it was built from, and `versionCode` is monotonic by construction. `workflow_dispatch` with an explicit tag exists for re-releases, not for a second way to publish.
  2. **A tag must pass the pull-request gate.** The `verify` job runs the same `npm run check` as `ci.yml` (tsc, ESLint guardrails, Vitest coverage thresholds, Playwright e2e) and both build jobs depend on it. A tag that would not survive review cannot publish. The alternative — depending on `ci.yml` through `workflow_run` — was rejected: release correctness should not be a cross-workflow coupling.
  3. **Signing failures are build failures, not warnings.** The job fails before Gradle if any of the four `ANDROID_*` secrets is empty, decodes the keystore, and then asserts with `apksigner verify --print-certs` that each APK is signed and is *not* `CN=Android Debug`. The silent-unsigned-APK path that `build.gradle` keeps for clean-checkout debug builds therefore cannot reach a release.
  4. **Verification is in the pipeline, not in a checklist.** `aapt2 dump badging` asserts in CI what Rule 15 asks a human to check on a device: the TV APK is leanback-launchable, requires `android.software.leanback` and marks the touchscreen as not required; the mobile APK does none of those; and both carry the tag's `versionCode`/`versionName`. The instrumented `MainActivityImeTest` suite is deliberately *not* in the pipeline — it needs an emulator plus a device matrix that would dwarf the build, and it is guarding a native WebView focus behaviour that no release step touches.
  5. **`gh` CLI, not a third-party release action.** `gh release create --verify-tag` with the workflow's own `GITHUB_TOKEN` (`contents: write` on that job alone) keeps the supply chain to actions already trusted in this repo (`checkout`, `setup-node`, `setup-java`, `upload/download-artifact`) and given `gh` is preinstalled, one less pinned dependency. Release notes are generated from the commit range between the previous tag and this one, so the notes and the artifacts describe the same commits.
  6. **Re-running is idempotent.** The release job edits an existing release and re-uploads with `--clobber` instead of failing on a duplicate. A retried job or a deliberate re-release must not require hand-deleting a release first.
  7. **`scripts/release.sh` owns the tag, not the build.** It refuses a dirty tree, a non-`main` branch or a `HEAD` behind `origin/main`, then creates an *annotated* tag carrying the same `Signed-off-by:` trailer that `CONTRIBUTING.md` and the DCO workflow require of commits. Sign-off is a property of the contribution, and a release tag is a contribution.
- **Consequence:** Publishing is `scripts/release.sh patch --push`, and the assets (web zip, two signed APKs, two AABs, `SHA256SUMS.txt`) appear on the GitHub Release without a manual step. Per-form-factor versions can no longer drift because they come from one tag. The cost is a duplicated `npm run check` on tagged commits (also run by `ci.yml`) and four repository secrets whose loss is unrecoverable — documented in `docs/RELEASING.md` §3 and §4, alongside the deliberate scope boundary around instrumented tests.

### ADR 025: The channel-switch tone is synthesised, fired from the channel id, and opt-out
- **Context:** Zapping between channels had no feedback beyond the Now/Next banner, which is slow to read and invisible over a busy picture. A confirmation tone is the fastest possible "the remote was received" signal on a 10-foot UI, but it must not become an asset to download, a second media element competing with the player, or an unavoidable annoyance.
- **Decision:**
  1. **Synthesised, not sampled.** `src/services/audio/channelSwitchSound.ts` builds the blip from a Web Audio `OscillatorNode` (sine, 660→990 Hz, ~120 ms) and a `GainNode` envelope. There is no audio file to fetch or cache, no bundle bytes, and no `<audio>` element the player engine could reclaim.
  2. **One code path for every switch.** The tone is triggered by a `useEffect` keyed on `channel.id` inside `PlayerView`, not by the individual handlers. Selecting a channel card (which mounts `PlayerView`), `CH_UP`/`CH_DOWN`, the number zap, and the mini channel list all end up as a new `channel.id`, so all of them get the sound with no per-handler call sites to drift. The first mount counts as a tune-in and plays the tone too — it is a channel switch from the viewer's point of view, and skipping it was the original bug. Flipping the preference itself changes no channel id, so it never replays the tone.
  3. **Lazy context, best-effort playback.** The `AudioContext` is created on the first switch, which is inside a remote-key gesture, so the autoplay policy does not suspend it; a suspended context is `resume()`d but a failure is swallowed. Audio must never delay or block the channel change it confirms.
  4. **Opt-out in Settings → Playback.** `AppSettings.channelSwitchSound` (default `true`) is the single switch, surfaced as a focusable tile like the surrounding playback controls. No hidden gesture and no per-surface override.
- **Consequence:** Zapping and tuning in give immediate audio confirmation on every path — player keys, number zap, mini list, and selecting a card on Home / Live TV / Guide / Favorites / Search — with no asset and no new dependency. The trade-off is that Web Audio runs on the page's own audio output alongside the stream, so a user who wants silence uses the setting, and the Android shell inherits exactly the browser's audio behaviour — no native change is involved.
